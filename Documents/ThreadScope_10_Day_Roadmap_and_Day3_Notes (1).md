# Day 3 Revision Notes --- Thread-Safe Event Collector

## 1. Today's objective

Build a thread-safe event collector that records activities generated by
multiple threads.

ThreadScope needs to record events such as:

-   A thread starting.
-   A thread performing work.
-   A thread requesting a lock.
-   A thread acquiring or releasing a resource.
-   A thread finishing.

The event collector stores these records so that they can later be
processed and visualized.

## 2. ThreadEvent structure

A `struct` groups related variables into one unit.

``` cpp
struct ThreadEvent {
    int threadId;
    string eventType;
    long long timestamp;
    int resourceId;
};
```

Fields:

  -----------------------------------------------------------------------
  Field                               Meaning
  ----------------------------------- -----------------------------------
  `threadId`                          Identifies the thread that
                                      generated the event

  `eventType`                         Describes what happened, such as
                                      `START`, `WORKING` or `FINISH`

  `timestamp`                         Records when the event occurred

  `resourceId`                        Identifies the associated resource;
                                      use `-1` when no resource is
                                      involved
  -----------------------------------------------------------------------

Example:

``` cpp
ThreadEvent event;

event.threadId = 1;
event.eventType = "START";
event.timestamp = 100;
event.resourceId = -1;
```

## 3. Why do we need a thread-safe collector?

We use a shared vector to store events:

``` cpp
vector<ThreadEvent> events;
mutex eventsMutex;
```

Multiple threads may try to insert events into the same vector.

Calling `events.push_back(event)` concurrently without synchronization
can cause a data race and undefined behavior because multiple threads
may modify the vector's internal state simultaneously.

### Solution: protect the vector with a mutex

``` cpp
void producer(ThreadEvent event) {
    lock_guard<mutex> lock(eventsMutex);
    events.push_back(event);
}
```

What happens:

1.  The thread attempts to acquire the mutex.
2.  If another thread holds it, the thread waits.
3.  Once the mutex is acquired, the event is inserted.
4.  When the lock object goes out of scope, the mutex is automatically
    released.

This ensures that only one thread at a time modifies the shared vector
through this function.

## 4. `lock_guard` vs. `unique_lock`

Both provide automatic unlocking when their lock object goes out of
scope.

  Feature                                   `lock_guard`   `unique_lock`
  ----------------------------------------- -------------- ---------------
  Automatically locks by default            Yes            Yes
  Automatically unlocks                     Yes            Yes
  Manual unlock                             No             Yes
  Can lock again after unlocking            No             Yes
  Works with `condition_variable::wait()`   No             Yes

### `lock_guard`

Use it for simple critical sections where the mutex only needs to be
locked and automatically released.

``` cpp
{
    lock_guard<mutex> lock(eventsMutex);
    events.push_back(event);
}
```

### `unique_lock`

Use it when more control over the mutex is needed.

``` cpp
unique_lock<mutex> lock(eventsMutex);

lock.unlock();  // Release mutex
lock.lock();    // Acquire it again
```

**Remember:** `condition_variable::wait()` requires a `unique_lock`
because it temporarily releases the mutex while the thread waits and
reacquires it before returning.

## 5. Condition variable

### Problem: busy waiting

Suppose a consumer needs to process items from a queue.

It could repeatedly check:

``` cpp
while (q.empty()) {
    // Keep checking
}
```

This is called busy waiting.

The CPU keeps executing the loop even though there is no useful work to
perform.

### Solution: `condition_variable`

A condition variable allows a thread to sleep until it is notified that
something potentially useful has happened.

``` cpp
mutex m;
condition_variable cv;
queue<int> q;
```

Waiting:

``` cpp
unique_lock<mutex> lock(m);

cv.wait(lock, [&]() {
    return !q.empty();
});
```

Notification:

``` cpp
cv.notify_one();
```

### How `wait()` works

1.  The consumer acquires the mutex.
2.  It checks the condition.
3.  If the queue is empty, `wait()` releases the mutex and puts the
    consumer thread to sleep.
4.  A producer can acquire the mutex and insert an item.
5.  The producer notifies a waiting consumer.
6.  The consumer wakes up and reacquires the mutex.
7.  The predicate is checked again.
8.  If the condition is true, execution continues.

Important: the consumer thread sleeps; the mutex is temporarily
unlocked. The mutex itself does not sleep.

Use the predicate form of `wait()` because wakeups can occur without the
condition being satisfied, including spurious wakeups.

### `notify_one()` vs. `notify_all()`

-   `notify_one()` wakes one waiting thread.
-   `notify_all()` wakes all waiting threads.

## 6. Producer-consumer concept

The producer-consumer pattern separates event generation from event
processing.

**Producer:** - Generates an item or event. - Adds it to a shared
queue. - Notifies a consumer.

**Consumer:** - Waits if the queue is empty. - Wakes when notified. -
Removes and processes an item.

A simplified producer operation:

``` cpp
{
    lock_guard<mutex> lock(m);
    q.push(value);
}

cv.notify_one();
```

A simplified consumer operation:

``` cpp
unique_lock<mutex> lock(m);

cv.wait(lock, [&]() {
    return !q.empty();
});

int value = q.front();
q.pop();
```

For the Day 3 ThreadScope deliverable, the required implementation is a
mutex-protected shared vector. The producer-consumer queue is a
supporting concept; it does not have to be integrated into the event
collector yet.

## 7. The `join()` function and safe printing

After creating worker threads, join them:

``` cpp
for (thread& worker : threads) {
    worker.join();
}
```

`join()` makes the main thread wait until each worker thread finishes.

After all worker threads have been joined:

-   All event-generation calls have completed.
-   No worker thread is still modifying the vector.
-   The main thread can safely read and print the vector without
    acquiring the mutex again.

Important: `join()` does not guarantee that events appear in thread-ID
order. The order depends on thread scheduling and execution timing.

## 8. Timestamp helper function

Instead of repeating a long timestamp expression every time, create a
helper function:

``` cpp
long long getTimestamp() {
    return chrono::duration_cast<chrono::milliseconds>(
        chrono::system_clock::now().time_since_epoch()
    ).count();
}
```

Then use:

``` cpp
event.timestamp = getTimestamp();
```

Include:

``` cpp
#include <chrono>
```

This Day 3 helper uses `system_clock`. In Day 4, the roadmap introduces
`steady_clock` for measuring elapsed time relative to program start.

## 9. Day 3 implementation

The following implementation creates six threads. Each thread generates
three events and safely inserts them into the shared vector.

``` cpp
#include <iostream>
#include <chrono>
#include <thread>
#include <mutex>
#include <vector>
#include <string>

using namespace std;

struct ThreadEvent {
    int threadId;
    string eventType;
    long long timestamp;
    int resourceId;
};

vector<ThreadEvent> events;
mutex eventsMutex;

long long getTimestamp() {
    return chrono::duration_cast<chrono::milliseconds>(
        chrono::system_clock::now().time_since_epoch()
    ).count();
}

void producer(ThreadEvent event) {
    lock_guard<mutex> lock(eventsMutex);
    events.push_back(event);
}

void generateEvents(int threadId) {
    for (const char* eventType : {"START", "WORKING", "FINISH"}) {
        ThreadEvent event;

        event.threadId = threadId;
        event.eventType = eventType;
        event.timestamp = getTimestamp();
        event.resourceId = -1;

        producer(event);
    }
}

int main() {
    vector<thread> threads;

    for (int threadId = 1; threadId <= 6; ++threadId) {
        threads.emplace_back(generateEvents, threadId);
    }

    for (thread& worker : threads) {
        worker.join();
    }

    for (const ThreadEvent& event : events) {
        cout << "Thread " << event.threadId
             << " | " << event.eventType
             << " | timestamp: " << event.timestamp
             << " | resource: " << event.resourceId << '\n';
    }

    return 0;
}
```

### Expected result

-   Six threads are created.
-   Each thread generates three events.
-   Every event is inserted using the mutex-protected `producer()`
    function.
-   All threads are joined.
-   The collected events are printed.

Total expected events:

**6 threads × 3 events = 18 events**

The order of printed events may vary between runs.

## 10. Important interview questions

**Q1. Why can't multiple threads directly call `push_back()` on the same
shared vector without synchronization?**

Because concurrent modifications can cause a data race and undefined
behavior by interfering with the vector's internal state.

**Q2. Why choose `unique_lock` over `lock_guard`?**

`unique_lock` offers more control, including manual unlocking and
relocking. It is also required by `condition_variable::wait()`.

**Q3. What happens when Thread 1 holds a mutex and Thread 2 tries to
acquire it?**

Thread 2 waits until Thread 1 releases the mutex. It can then acquire
the mutex and enter the protected section.

**Q4. What is busy waiting?**

Repeatedly checking a condition instead of sleeping while waiting for
work. It wastes CPU cycles.

**Q5. What happens to the mutex during `condition_variable::wait()`?**

The waiting thread temporarily releases the mutex, sleeps, then
reacquires it before continuing.

**Q6. Why use `notify_one()`?**

To wake one waiting thread so it can check whether work is available.

**Q7. Why don't we need another mutex when printing after joining all
threads?**

Because all worker threads have finished, so no thread is modifying the
vector while the main thread reads it.

**Q8. Does `join()` guarantee event ordering?**

No. It guarantees that the joined thread has completed. It does not
guarantee the order in which different threads generated their events.

## 11. Day 3 key takeaways

-   A shared vector needs synchronization when multiple threads modify
    it.
-   A mutex protects a critical section.
-   `lock_guard` is suitable for simple automatic locking and unlocking.
-   `unique_lock` provides flexible lock control.
-   `condition_variable` allows threads to wait without busy waiting.
-   Producer-consumer separates event generation from event processing.
-   `join()` ensures worker threads finish before the main thread reads
    the collected events.
-   A helper function keeps timestamp generation clean and reusable.
